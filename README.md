# Мониторинг сервисов на Grafana Alloy

Светофор доступности: имя сервиса и рядом цвет — зелёный, жёлтый, красный.
Собирает всё один агент Alloy, отдаёт в существующий Prometheus, рисует
Grafana. Разворачивается Ansible-ролью, одинаково на стенде и на проде.

## Переменные: обязательных всего две

```yaml
mon_networks:                 # сети, в которые включается Alloy
  - app_net
  - monitoring_net

mon_services:                 # что мониторим
  - name: redis
    group: infra
    probe: {module: tcp_connect, address: "redis:6379"}
```

Всё остальное имеет умолчания в `roles/monitoring/defaults/main.yml`.
Раскладку дашборда роль выводит из `mon_services` сама — по строке на группу
во всю ширину; задавать `mon_groups` нужно только для многоколоночной
раскладки.

Полный список переменных с умолчаниями — в
[roles/monitoring/README.md](ansible/roles/monitoring/README.md).

## Перенос на другой сервер или в другой репозиторий

Роль самодостаточна и использует только `ansible.builtin` — коллекции
ставить не нужно.

```bash
cp -r ansible/roles/monitoring /path/to/your-repo/roles/
```

Дальше подключаете её обычным образом:

```yaml
- hosts: my-server
  roles:
    - role: monitoring
      vars:
        mon_networks: [app_net, monitoring_net]
        mon_services: [...]
```

Каталог `ansible/` целиком — это готовый пример обвязки: инвентарь,
плейбук и `group_vars`.

## Перенос: составить список сервисов автоматически

Выписывать два десятка сервисов руками не нужно. На сервере:

```bash
# 1. Какие сети есть и кто в них - отсюда берётся mon_networks
./scripts/show_networks.sh

# 2. Черновик mon_services по работающим контейнерам
python3 scripts/discover_services.py > draft.yml
```

`discover_services.py` не гадает по портам, а **проверяет** health- и
metrics-эндпоинты по-настоящему — изнутри docker-сети, одним вспомогательным
контейнером на сеть. Что ответило 2xx, попадает в `http_2xx`; остальное — в
`tcp_connect`. Заодно распознаёт Redis и Elasticsearch и проставляет им
`exporter`.

Черновик нужно вычитать: группы угаданы по имени образа, а часть контейнеров
(сам Prometheus, Grafana, cAdvisor) мониторить через этот дашборд обычно не
нужно. Скопируйте отобранное в `group_vars/prod.yml`.

Проверено на стенде: из 29 контейнеров скрипт собрал 28 сервисов, правильно
определил Redis как TCP с экспортером, Zeebe — как `/actuator/health` плюс
`/actuator/prometheus`, и результат прошёл валидацию роли без правок.

## Развёртывание

```bash
cp ansible/group_vars/prod.yml.example ansible/group_vars/prod.yml
vim ansible/group_vars/prod.yml          # свои имена контейнеров
cd ansible
ansible-playbook -i inventory.yml site.yml -l prod
```

Только перегенерировать конфиги, не трогая работающий агент:

```bash
ansible-playbook -i inventory.yml site.yml -l prod --skip-tags deploy
```

На стенде в WSL Ansible ставить не нужно — он запускается в контейнере:

```bash
./lab.sh up       # среда + psi-stack + мониторинг
./lab.sh deploy   # только мониторинг
```

### Что требуется от сервера

1. Docker и `docker compose`.
2. Prometheus с `--web.enable-remote-write-receiver` — Alloy пушит метрики,
   без флага писать некуда.
3. Prometheus с `--web.enable-lifecycle` — иначе правила подхватятся только
   после перезапуска.
4. `mon_rules_dir` смонтирован в Prometheus, `mon_dashboards_dir` — в Grafana.
5. Сети из `mon_networks` существуют.

Пункты 2, 3 и 5 роль проверяет сама и останавливается с внятной ошибкой.
Отключается через `mon_preflight: false`.

Перед перезапуском агента проверяются синтаксис конфига Alloy, правила через
`promtool` и валидность JSON дашборда; после подъёма роль ждёт ответа от
`/-/ready`. Повторный прогон даёт `changed=0`.

## Как описывается сервис

```yaml
- name: my-python-worker-01     # обязательно: подпись и метка service
  group: workers                # обязательно: колонка дашборда
  kind: worker                  # необязательно: метка kind
  probe:                        # обязательно: чем проверять доступность
    module: http_2xx            #   http_2xx | http_any | tcp_connect
    address: "http://my-python-worker-01:8080/health"
  metrics:                      # необязательно: свои метрики сервиса
    address: "my-python-worker-01:8080"
    path: /metrics
  exporter: redis               # необязательно: родной экспортер Alloy
  exporter_address: "redis:6379"
```

Адреса пишутся так, как их видит Alloy изнутри docker-сети, то есть
`<имя контейнера или сетевой алиас>:<порт>`. Посмотреть имена:
`docker ps --format '{{.Names}}'`.

Роль проверяет каждый элемент списка и падает с указанием конкретного
сервиса, если чего-то не хватает.

## Чем проверять: модули проб

| Модуль | Что делает | Что засчитывается как «жив» |
|---|---|---|
| `http_2xx` | GET по адресу | ответ 2xx |
| `http_any` | GET по адресу | любой ответ из списка (200, 401, 403, 503…) |
| `tcp_connect` | DNS + TCP-рукопожатие | соединение установилось |

### Ограничение tcp_connect

`tcp_connect` не отправляет ни байта данных: он резолвит имя, открывает
сокет и закрывает его. Метрик у него ровно четыре — `probe_success`,
`probe_duration_seconds`, `probe_dns_lookup_time_seconds`,
`probe_ip_protocol`. Ни статуса, ни тела ответа нет, потому что протокол
поверх TCP пробе неизвестен.

Отсюда его слепое пятно: **соединение принимает ядро, а не процесс.**
Пока слушающий сокет открыт, TCP-рукопожатие проходит из backlog даже если
процесс заморожен, зациклен или не отвечает.

Проверено на стенде: `docker pause monlab-redis` — `redis-cli ping` виснет
по таймауту, то есть сервис для клиентов мёртв, а `probe_success` при этом
остаётся `1`.

### Чем это закрыто

Для сервисов с родным экспортером в статус входит правило
`<префикс>:service_reachable` — мнение экспортера о доступности сервиса:

| exporter | метрика (`mon_exporter_up_metrics`) |
|---|---|
| `redis` | `redis_up` |
| `elasticsearch` | `elasticsearch_cluster_health_up` |

Если экспортер говорит `0`, сервис становится **красным**, даже когда
TCP-проба зелёная. На том же замороженном Redis: `probe_success = 1`,
`redis_up = 0`, итоговый статус `0`. Сервисы без экспортера получают `1`
и оцениваются только по пробе — отсутствие экспортера не красит их в красный.

### Что из этого следует для ваших сервисов

`tcp_connect` — вариант последнего выбора, когда у сервиса нет ни HTTP,
ни экспортера. Он честно ловит «процесс упал», «контейнер остановлен»,
«порт не слушается», но не отличает живой сервис от зависшего.

Порядок предпочтения:

1. `http_2xx` на настоящий health-эндпоинт — проверяет и порт, и логику;
2. `tcp_connect` + родной экспортер — проба ловит падение, экспортер зависание;
3. `tcp_connect` в одиночку — только для сервисов, где ничего другого нет.

Для сервисов на Python, C# и C++ дешевле всего добавить в приложение
`/health` и `/metrics` с полем `app_degraded` — тогда сервис сам сообщает
о деградации, и это попадает в жёлтый через источник `app`.

## Как считается цвет

Всё сводится к одной метрике `<префикс>:service_status`:

| Значение | Цвет | Условие |
|---|---|---|
| 0 | красный | blackbox-проба не проходит |
| 1 | жёлтый | проба проходит, но есть признак деградации |
| 2 | зелёный | проба проходит, признаков деградации нет |

Источники жёлтого — метка `src` в `<префикс>:service_degraded`:

| src | Что значит |
|---|---|
| `slow` | проба отвечает дольше `mon_slow_probe_seconds` |
| `app` | приложение само выставило `app_degraded 1` |
| `es_yellow` | статус кластера Elasticsearch — yellow |
| `redis` | не прошёл bgsave либо занято >90% maxmemory |
| `zeebe` | `zeebe_health` партиции не равен 1 |

Алерты считаются из тех же выражений, поэтому панель и алерт не могут
разойтись.

Цвет на дашборде задаётся **порогами**, а не цветом из value mappings: stat
берёт цвет из mappings, а state-timeline красит регионы по порогам и mappings
игнорирует. За mappings остались только подписи.

## Панели диска

Их две, и они отвечают на разные вопросы — раньше это была одна панель
с заголовком «свободное место» и числом занятого, что читалось неверно.

| Панель | Метрика | Смысл |
|---|---|---|
| Свободно на диске | `<префикс>:disk_avail_bytes` | сколько осталось, в байтах |
| Занято на диске | `<префикс>:disk_used_ratio` | доля занятого, 0…1 |

Пороги независимы: «свободно» желтеет ниже `mon_disk_free_warn_gib` (50 ГиБ)
и краснеет ниже `mon_disk_free_crit_gib` (10 ГиБ); «занято» желтеет от 80%
и краснеет от 90%. На большом диске это разные события, поэтому и пороги
разные.

## Почему инвентарь статический

`discovery.docker` видит только запущенные контейнеры. Если вести список
проб через него, упавший сервис просто исчезнет из мониторинга:
`probe_success` перестанет писаться и панель покажет «нет данных» вместо
красного — ровно тогда, когда красный и нужен.

Поэтому `mon_services` — это декларация «эти сервисы обязаны работать».
Проверено: остановленный контейнер даёт статус 0, а не пропажу с дашборда.

## Проверка

```bash
./lab.sh check    # агент, цели, доставка, запросы всех панелей
./lab.sh status   # светофор в терминале
```

Сквозная проверка цветов — сломать сервис и посмотреть:

```bash
./lab.sh chaos degrade py-worker-03   # жёлтый
./lab.sh chaos down    py-service-01  # красный (503 на /health)
./lab.sh chaos stop    cs-service-02  # красный (контейнера нет)
./lab.sh chaos reset                  # вернуть всё
```

Цвет меняется за 15–30 секунд: проба плюс интервал правила.

## Известные ограничения

- Hazelcast без Management Center не отдаёт Prometheus-метрик, поэтому для
  него доступны только красный и зелёный.
- У Keycloak метрики есть, но осмысленного признака деградации не нашлось —
  он желтеет только по медленной пробе.
- `psi_exporter` из psi-stack собирается из `/mnt/d/git-repos/shiny-robot`,
  где сейчас пустое рабочее дерево. Контейнер живёт на собранном образе, но
  `docker compose build` в psi-stack упадёт, пока не сделан `git restore .`.
